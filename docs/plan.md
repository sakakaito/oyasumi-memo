## 0. 全体像

### MVP のゴール（backlog §4）
> 検索で紹介ページに来る → その場で夜の画面を開く → 声（またはテキスト）で預ける／今日の日記を話す → 朝に分類つきで見て片付ける → 日記を読み返せる

この一周が iPhone（Safari のタブ／ホーム画面アプリ）で回ること。対象は backlog の「MVP ○」のストーリー 25 件。

### フェーズ4：声で預ける・声で日記

## 3. 未決事項がどのフェーズを止めるか

- 「止める」＝その判断が出ないと、そのフェーズを**完了**できない（または着手できない）
- 「止めない」＝仮の値や仮の置き方で先に進め、答えが出たら直す
- 期限の目安は「その判断が無いと作り直しが大きくなる前」で置いた。確定の期日ではない

## 4. リスクと対策

### 4-1. iPhone の音声認識の制約

| リスク | 起きると | 対策 |
|---|---|---|
| ホーム画面アプリで Web Speech API が使えない（WebKit Bug 225298、修正の確認なし） | ホーム画面アプリで声のボタンが動かない | 方式K（キーボードの音声入力）をどの結果でも作る（4-A1）。環境で W/K を選ぶ（4-B2）。テキスト入力はいつでも使える（§12） |
| 「音声入力」の設定がオフだと `service-not-allowed` で失敗する | 夜中に原因がわからない | エラーごとの直し方を夜の配色で出す（US-06）。初回の案内でオンにしておく（US-43） |
| マイクの許可を毎回聞かれる | 毎晩白いダイアログ（§13 で致命的） | フェーズ0 で最優先に確かめる。毎回出るなら方式K を本命にし、4-B を小さくする。そのため音声の実装を結果待ちのフェーズ4 に置いた |
| 連続モードで文字が確定しない | 話した内容が保存されない | 試作 v2 の「連続モードを使わずつなぎ直す」処理を移して使う（4-B1） |
| 無音で止まるまでの時間が端末で違う | 寝落ちしたときに保存されない | 秒数を 1 か所の設定値にし（4-A3）、画面が消えたときも保存する（4-A2）。秒数は実機の結果で決める |
| 声を文字にする機能は通信がないと使えない場合がある（未確認） | 機内モードで声が使えない | US-06 の案内でテキストへ移れるようにする（US-41） |
| 音声は PC で確かめられない | 実機の確認がオーナー頼みになり、進みが遅くなる | 確認は 1 回 10 分ほどで終わる手順にまとめる（TE）。試作の「結果をコピー」のように、結果を貼るだけで済む形にする |

### 4-2. Safari とホーム画面アプリでデータが分かれる

iPhone では、Safari のタブで保存したデータは、ホーム画面に追加したアプリからは見えない（§13 案F の注意）。

| リスク | 起きると | 対策 |
|---|---|---|
| 検索から来て Safari で使い始めた人が、あとでホーム画面に追加する | 前のメモ・日記が見えず、消えたと思われる | 追加する前に「引き継がれない」ことを伝える（US-42）。エクスポートは MVP に入れる（US-31）。インポート（US-35）は確認2 で Must に上げるか決める |
| Safari のタブでは、しばらく開かないサイトのデータが消されることがある（ホーム画面アプリは対象外と WebKit が公表。実機は未確認） | Safari だけで使う人のデータが消える | ホーム画面への追加をすすめる（US-42）。`navigator.storage.persist()`（US-36）の前倒しを PO に提案 |
| 公開後に公開先やドメインを変える | 保存場所（オリジン）が変わり、利用者のデータが新しい URL に引き継がれない。検索の評価も一からになりやすい | **確認3 を公開前に決める**（§3-2）。決まるまでは利用者を呼ばない（紹介ページは `noindex`） |
| `sakakaito.github.io` は、同じアカウントの他の GitHub Pages とも保存場所を共有する。試作も localStorage を使っている | 名前がぶつかるとデータが混ざる | データベース名をこのアプリ固有にする（2-A）。試作のデータには触れない |
| オーナー自身の確認で、Safari とホーム画面アプリのデータが違って見える | 不具合と見分けがつかない | 確認手順に「どちらで開いたか」を書く欄を作る（TE）。開発中のデータは消えてもよい確認用と割り切る |

### 4-3. GitHub Pages で本番アプリをビルドして公開する方法と、試作ページを残す方法

**今の状態**：`main` の中身をそのまま公開している（ビルドなし、`.nojekyll` あり）。試作は `/oyasumi-memo/prototype/voice-test/`。

**やり方（提案）**：GitHub Actions でビルドして公開する

```
main に push
  → npm ci → npm test → npm run build（SEO 点検を含む）
  → dist/ に prototype/ をそのままコピー（試作は Vite に通さない）
  → GitHub Pages に公開（公式の upload-pages-artifact / deploy-pages を使う）
```

| 決めること | 案 | 理由 |
|---|---|---|
| 公開の方式 | GitHub Actions（Settings → Pages → Source を「GitHub Actions」に） | ビルドの成果物をリポジトリに入れずに済む。公開リポジトリなら無料（0 円の目標） |
| 別の案 | ビルド結果を `gh-pages` ブランチや `docs/` に入れる | 採らない。`docs/` は文書置き場で、成果物が混ざる |
| 試作の残し方 | ファイルは今の場所 `prototype/` のまま動かさず、ビルドのあとにコピー | URL・ホーム画面に追加済みの試作アイコン・git の履歴がそのまま残る |
| 画面の切り替え | ルーターを使わず React の状態で切り替える | GitHub Pages では `/app/morning` のような URL を直接開くと 404 になる。依存も減る |
| 公開先のパス | Vite の `base` を設定値に（今は `/oyasumi-memo/`） | 独自ドメインや Cloudflare Pages になっても 1 か所で済む |
| Service Worker の範囲 | `/oyasumi-memo/app/` に限る | 試作ページや紹介ページを古いまま保存してしまうのを防ぐ（試作には Service Worker が無いことを確認済み） |

| リスク | 対策 |
|---|---|
| Source を切り替えた直後にワークフローが失敗し、試作の URL まで 404 になる | 先にワークフローを入れて Actions のビルドが通るのを確かめてから切り替える。だめなら Source を「main ブランチ」に戻せば今の状態に戻る |
| Source の切り替えはリポジトリの設定変更 | オーナーが行う（1-E）。まとめ役は手順を案内する |
| 壊れた版を公開してしまう | テストと SEO 点検が通らなければ公開まで進まないワークフローにする。戻すときは commit を戻して push |
| 新しい版の公開で、夜の画面が突然再読み込みされる | 自動で入れ替えず、次に開いたときか朝の画面で反映する（5-B・US-44） |
